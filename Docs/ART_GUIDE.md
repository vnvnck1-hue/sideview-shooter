## 0. 최상위 제작 원칙 — 승인 원화 보존 (v1.13)

**자연어 요청 → 기존 리소스의 그림체 가이드로 원화 생성 → 사용자 원화 승인 → Aseprite에서 원화 보존 중심의 실제 픽셀화 → 보존·게임 적용 검수**가 기본 프로세스다. 픽셀화는 새 디자인을 만드는 단계가 아니다.

### 단계별 책임과 우선순위

1. **원화 생성:** 사용자 요청과 기존 리소스를 근거로 색감, 실루엣·비율, 약한 원근, 명암 덩어리, 재질, 외곽선, 디테일 밀도를 반영한다. 아래 그림체 규칙은 우선 이 단계에서 적용한다. 기준 이미지 경로와 비교 근거를 함께 남긴다.
2. **사용자 승인:** 승인된 원본 파일·버전·SHA256, 시트 안의 대상 영역, 승인 범위와 수정 요청을 기록한다. 승인 원화는 불변으로 보존한다. 원화 승인은 디자인 기준 확정이며 게임 반입 승인은 아니다.
3. **보존 브리프:** 원화의 형태·부품 수와 배치·색온도·명도 관계·재질·마모·발광 위치·핵심 디테일을 보존 목록으로 만든다. 기존 원화의 디자인이 픽셀화 결과의 직접 기준이며, 다른 기존 프랍은 게임 내 일관성 검토용이다.
4. **Aseprite 픽셀화:** 원화에 대응하는 격자 위에서 픽셀 배치·색·경계를 통제한다. 원화 참조/오버레이를 보며 옮기고 픽셀화에 필요한 국소 정리를 한다. 임의로 재설계, 부품 삭제·추가, 비율·원근 변경, 재색칠, 명암 평탄화를 하지 않는다. 펜·Lua·자동화는 수단일 뿐이며 `.aseprite` 확장자만으로 실제 픽셀 작업이나 충실도가 증명되지 않는다.
5. **두 가지 검수:** 승인 원화와의 보존 비교를 먼저 하고, 기존 게임 리소스·플레이어·배경과의 적용 비교를 별도로 한다. 원화의 표정이 바뀌었다면 규격 검사가 통과해도 실패다. 불가피한 변화는 변경 부위·이유·손실을 보여 주고 사용자 승인을 받는다.
6. **선택 반입:** 픽셀화 결과 승인 및 호환성 확인 뒤 허용된 파일만 반입한다. 실제 엔진의 줌·빛·가림·접지를 확인한다. 원화 승인만으로 자동 배포하지 않는다.

**보존 우선:** 기존의 작은 캔버스나 색 수 제한을 지키기 위해 승인 원화의 매력을 크게 줄이지 않는다. 손실이 크면 제작을 중단하고 규격을 먼저 재검토한다. 새 그림체 해석이 필요하면 픽셀화 안에서 몰래 수행하지 말고 원화 승인 단계로 돌아간다. 이후 절의 단순화·군집·형태 정리 규칙도 이 원칙 아래에서 적용한다.

### 해상도·팔레트 결정은 손실 검토 뒤에

- **캐릭터는 자산당 8~16색 목표를 유지한다.** 배경과 구별되는 간결한 색면과 판독성을 위한 사용자 지정 원칙이다. 원화 생성부터 적용하며 세부 기준은 `CHARACTER_ART_GUIDE.md` §4를 따른다. 승인 후 기계적으로 감색해 디자인을 훼손하지 말고, 목표와 보존이 충돌하면 비교 후 다시 합의한다.
- **배경·프랍에는 8~16색 일괄 상한을 적용하지 않는다.** 원화의 재질과 색 관계를 보존하는 색 수를 자산별로 정하고 브리프/검사에 같은 값을 기록한다. 다른 고정 상한(예: 32/64색)으로 일괄 대체하지 않는다.
- 과거 연구시설 생성기의 `55×59`, `63×48`, `61×88` 등은 원화 충실도가 검증된 납품 규격이 아니다. 그대로 고정해 재사용하지 않는다. 기존 캐릭터·타일·방의 규격까지 자동 해제되는 것은 아니다.
- 대표 프랍 하나에서 전체와 고밀도 부분을 함께 보고, 현행 크기와 더 높은 네이티브 해상도 후보의 **보존 손실**을 비교한다. 크기 숫자만 보고 합격시키거나 시트 해상도를 그대로 에셋 해상도로 쓰지 않는다.
- 현재 구현은 `월드 크기 = 네이티브 크기 × 4`, `화면 크기 = 네이티브 크기 × 4 × 카메라 zoom`이다. 같은 물체를 2배 해상도로 만들고 ×4 반입하면 월드 크기도 2배다. 월드 크기를 유지하려면 픽셀 단위/출력 배율과 카메라의 정수 배율, 기존 자산 혼용을 함께 설계해야 한다. 런타임 축소로 조용히 해결하지 않는다.
- 현재 4px 체계는 **현행 엔진 호환 프로파일**로 유지한다. 보존 손실이 크면 변경 후보로 검토하되, 새 프로파일은 비교 결과와 사용자 합의 및 코드 검증 전까지 미확정이다. 문서 변경만으로 게임 배율·카메라·배치·충돌 크기를 바꾸지 않는다.
- 모든 미세 차이의 무손실 보존을 미리 보장하지 않는다. 보존 실패를 ‘픽셀아트라 원래 단순해진다’로 정당화하지도 않는다. 손실이 큰 부위는 규격 대안과 함께 공개한다.

### 경계 선명도 보존 — 평균 축소 실패 반영 (v1.12)

- **픽셀화의 목적은 축소가 아니라 승인 원화의 경계·색면·디테일을 명확한 픽셀로 정리하는 것이다.** 원본 해상도를 유지하는 후보를 포함한다. 자동으로 가로·세로를 절반으로 줄이거나 공통 색 수를 먼저 강제하지 않는다.
- 원본의 밝은 선과 어두운 면을 공간 평균으로 섞으면 중간색이 생기고 얇은 틈·하이라이트가 사라진다. `2×2 평균 → 팔레트 축소 → 대비 강화`를 보존형 변환의 기본값으로 쓰지 않는다. 실패한 축소본에 강한 대비만 추가해서 보존 실패를 감추지 않는다.
- 경계 정리는 원본에서 시작한다. 양쪽 색면의 연속성과 원본의 선 두께를 보고 픽셀을 어느 면에 배치할지 선택한다. 원본에 없는 밝은 테두리·검은 링·새 색을 만들거나 단순 최근접 축소만으로 끝내지 않는다.
- 색 군집 정리는 비슷한 색의 흩어진 점을 제한적으로 묶되, 얇은 선·녹·천의 찢김·반사광을 보호한다. 알파 0/255만으로 내부 경계의 선명도가 증명되지는 않는다.
- 검수는 **원본 / 이전 변환 / 새 결과**의 같은 표시 크기와 동일 좌표의 정수배 확대를 모두 사용한다. 선 두께·모서리·밝은 띠·검은 틈·재질 무늬를 확인한다. 수치상 경계 유지율은 보조 자료이며 전체 그림체 보존율이나 사용자 승인 점수가 아니다.
- 이번 세 프랍의 원본 크기 유지 방식은 **사용자가 승인한 보존형 픽셀화 기준 프로세스**다. 기존 Native4 반입 배율 변경이나 고해상도 원본 전체를 항상 그대로 사용할 수 있다는 범용 규칙을 의미하지 않는다. 엔진 적용은 별도 승인이다.

### 승인된 기준 프로세스 — 이후 작업에서 재사용

2026-09-20 사용자 피드백: “이번에는 정말 거의 90% 이상 보존되었고, 선명도도 잘 보존되었어.” 이는 사용자의 시각적 평가이며 자동 측정한 보존율이 아니다. `ApprovedPropPixelTrial/crisp-final-r1/`의 세면대·캐비닛·의자를 승인된 변환 품질 기준으로 보존한다.

- 새 보존형 작업은 **승인 원본 → 원본 해상도 유지 우선 → 원본색 기반 색 군집 → 평균 없는 경계 정리 → 동일 크기/정수배 확대 비교 → Aseprite 재출력 검증**을 기본으로 시작한다.
- 구현 기준은 `Tools/Aseprite/preserve_crisp_prop.lua`, 재현 진입점은 `build_crisp_prop_trial.ps1`이다. 승인 시 설정은 `Tolerance=12`, `Snap=20`, `Coherent=true`, `Passes=3`. 이 수치는 출발점이며 다른 원화에서도 무조건 같은 품질을 보장하지 않는다.
- 2×2 평균 축소, 일괄 색 수 상한, 손실된 축소본의 대비만 증폭하는 과거 방식으로 되돌아가지 않는다. 결과가 기준보다 무뎌지거나 밀도가 줄면 제출 전에 원본과 다시 비교하고 원인을 수정한다.
- 승인 범위는 **이번 세 결과의 외관과 제작 프로세스**다. 신규 결과의 자동 승인, 게임 배율 변경, 기존 런타임 자산 교체까지 승인된 것은 아니다.

### 현재 승인 기준과 미완료 항목

현재 선택본·승인 범위·후속 피드백의 단일 관리 문서는 [`ART_ASSET_STATUS.md`](ART_ASSET_STATUS.md)다. 아래는 기준 사례 설명이며, 개별 실행의 `verification.json`은 당시 검사 스냅샷으로 보존한다.

- `Assets/Generated/ResearchFacilityV2/`의 analysis / isolation / diagnostics 프랍 시트는 사용자가 원하는 퀄리티·밀도로 명시한 **원화 보존 기준**이다. 형태뿐 아니라 컬러·디자인·명암·재질·디테일을 대상으로 한다. 같은 폴더의 벽 참고 이미지는 이번 프랍 승인에 포함시키지 않는다.
- `Assets/Generated/PropStyleLab/`은 이전 실패·비교 실험 기록이다. 특히 batch2 r4는 구조 검사에는 통과했지만 원화/기존 프랍과의 톤 불일치로 채택되지 않았다. 새 제작의 승인본이나 변환 기본값으로 쓰지 않는다.
- 이전 연구시설 생성기는 고정 좌표·색으로 다시 그리는 도구이며 원화 보존용으로 재사용하지 않는다. 이후 사용자가 직접 지정한 세면대·캐비닛·의자로 **원화 직접 입력 → 격자/팔레트 후보 비교 → Aseprite 국소 보정** 시험을 수행했다. [ApprovedPropPixelTrial 기록](../Assets/Generated/ApprovedPropPixelTrial/README.md)에 원본 대응·실제 손실·재출력 검사를 남겼다. 최신 `crisp-final-r1`의 외관과 프로세스는 사용자 승인되었으며 게임 반입은 미실행이다.
- 위 시험은 선택된 세 이미지의 보존 후보이지 모든 원화에 대한 품질 보증이나 새 엔진 규격 확정이 아니다. 최종 해상도와 실제 엔진 변경 여부가 정해지기 전에 연구시설 전체의 일괄 제작을 재개하지 않는다.
- 사용자 피드백에서 `final-r1`과 `contrast-r1`의 경계 둔화가 확인되어 기본 변환 방식으로 채택하지 않는다. 최신 승인본은 [crisp-final-r1](../Assets/Generated/ApprovedPropPixelTrial/crisp-final-r1/README.md)이다. 원본 크기를 유지하고 공간 평균 없이 Aseprite에서 색 군집·경계를 정리했다. 원본·이전본 비교와 자동 검사 및 사용자 외관 승인은 완료했으며 게임 반입은 별도 대기다.

### 픽셀 덩어리와 게임 배율은 별개다

| 용어 | 의미 | 의료실 예시 / 현행 엔진 |
|---|---|---|
| 원본 샘플링 간격 `pixelPitch` | 원본의 몇 px 구간을 네이티브 1px로 옮기는가 | 의료실 2.0: 원본 2×2 영역 → 아트 1px. 평균 RGB가 아닌 원본색 선택 |
| 네이티브 내용 크기 | 여백 제외 실제 픽셀 격자 | 1672×941 → 836×471 |
| 네이티브 캔버스 | 내용과 투명 여백을 포함한 파일 치수 | 네 면 1px 여백 → 838×473 |
| 게임 출력 배율 | 네이티브 1px당 월드 좌표 크기 | 현행 Native4는 ×4. 의료실의 게임 반입 규격은 미확정 |
| 화면 배율 | 게임 출력 배율 × 카메라 zoom | 현행 Native4의 ×2~×6. 원본 샘플링 간격과 무관 |

의료실은 3.0/4.0의 세부 손실 피드백 뒤 **2.0을 선택**했다. 이는 해당 원화의 선택이지 전 자산의 기본값이나 엔진을 2px 체계로 변경한다는 뜻이 아니다. 세 프랍의 원본 해상도 보존 기준도 유지한다. 자산별 변환 설정·실행 명령은 `ASEPRITE_PIPELINE.md`의 현재 실행 경로에 모은다.

방 전체 픽셀화는 일러스트 변환이다. 개별 프랍 분리·가려진 면 복원·타일 이음새·충돌·조명 분리가 완료된 게임용 모듈 제작과 구분한다. 추가 디자인이 필요한 분리·복원은 새 원화 검토 대상으로 기록한다.

## 1. 비주얼 방향

- 장르 표현: 어둡고 폐쇄적인 지하 공간의 사이드뷰 슈팅게임.
- 렌더링: 그림은 4px 블록 단위의 청키 픽셀 아트, 렌더는 창 해상도 풀해상도(2240×900). 확대는 카메라 줌이 맡고 화면 배율은 ×2~×6 사이를 오간다(§10). 조명·파티클·카메라 이동은 픽셀 격자에 묶지 않고 부드럽게 둔다 (2026-09-18 확정, §10).
- 형태 언어: 즉시 읽히는 실루엣과 조직된 픽셀 덩어리. 내부 묘사의 밀도는 기존 리소스와 승인 원화에 맞춘다. 픽셀화를 이유로 승인된 부품과 재질 묘사를 생략하지 않는다.
- 분위기: 낡고 불안하지만 플레이 정보는 명확하게 읽혀야 한다.
- 화면 우선순위: 캐릭터 > 상호작용 가능한 프랍 > 배경 구조물.
- 신규 방의 공간은 정비홀 v1·전력 릴레이실 v1 계열의 **넓지만 얕은 사이드뷰**를 따른다. 넓은 원근 바닥과 대형 근경으로 깊이를 늘린 정비홀 v2는 미채택이다. 근경은 방 기능에 맞게 새로 구성하되 게임 정보와 경쟁하지 않는다. 상세 기준과 참조는 `BACKGROUND_ART_DIRECTION.md`를 따른다.

## 2. 픽셀과 카메라

- 카메라는 사이드뷰 플레이를 기본으로 하되 프랍을 완전한 정사영 정면도로 평평하게 만들지 않는다.
- 프랍에는 윗면과 한쪽 측면이 소량 보이는 매우 약한 원근을 허용한다. 아이소메트릭 또는 강한 3/4 시점은 사용하지 않는다.
- 뒤벽과 주요 설비가 인물 가까이에 있고 좁은 바닥이 연속되는 얕은 측면 무대를 유지한다. 넓이는 가로로 이어지는 골조·덕트·장비 실루엣으로 만든다.
- 방의 큰 구조가 화면 밖으로 이어져도 된다. 외곽 프레임을 모두 노출하거나 검은 공간 속에 완결된 방 하나를 띄우는 구도를 새 배경의 필수 조건으로 삼지 않는다.
- 기존의 방 너비 85%·높이 70%, 너비 80% 미만 금지 및 외부 암부 여백은 **초기 디오라마 전시 구도의 이력**이다. 새 방에 고정 비율로 강제하지 않고 현재 선택된 시안과 실제 플레이 구도를 비교한다.
- 원화의 발 위치·인물 비율·화면 점유와 실제 게임 카메라는 별도다. 2026-09-22 조사 때는 2240×900, 기본 줌 0.75(화면 ×3)로 측정했으며, 이는 촬영 조건이지 새 카메라 설정 요청이 아니다. 허전함을 일괄 줌 증가, 캐릭터 축소 또는 깊은 지면 확장으로 해결하지 않는다.
- 한 장면 안에서 캐릭터, 프랍, 배경의 픽셀 크기를 통일한다.
- 안티앨리어싱, 부드러운 브러시, 미세한 노이즈 텍스처를 사용하지 않는다.
- 형태는 흩어진 잡점보다 의미 있는 픽셀 클러스터로 묘사한다. 승인 원화의 곡면·사선·비대칭을 직사각형으로 대체하라는 뜻은 아니다.
- 바닥은 플레이 가능한 연속 수평선으로 읽혀야 한다.

## 3. 컬러 역할 분리

배경과 상호작용 프랍을 동일한 국소 명암 폭·윤곽 강도·디테일 중요도로 묘사하지 않는다. **고유색을 보존하는 것이 전제**이며, 같은 색 계열도 역할에 따라 구분할 수 있다. 구분을 위해 프랍 전체를 다른 색상군으로 재색칠하는 것을 기본 해법으로 삼지 않는다.

### 배경 팔레트

- 차갑고 저채도인 청회색, 남보라, 차콜 계열을 사용한다.
- 프랍보다 명도 대비와 채도를 낮춘다.
- 균열, 벽돌, 파이프 같은 세부 요소는 넓고 조용한 색면으로 묶는다.
- 프랍 바로 뒤의 벽은 해당 프랍보다 어둡고 단순하게 유지한다.

### 프랍 팔레트

- 작업실의 따뜻한 웜그레이, 먼지 낀 갈색, 벽돌색, 적갈색은 기존 그림체 기준이다. 연구시설 등 별도 승인 원화의 회색·청남색·청록 기능색을 작업실 팔레트로 강제 치환하지 않는다.
- 최초 확정 프랍은 원화 생성 시 색·명암 기준으로 삼는다. 개별 원화 승인 이후에는 해당 원화의 명도, 채도, 색온도와 내부 음영 관계를 픽셀화의 직접 기준으로 보존한다.
- 배경과 분리하기 위해 프랍 자체를 밝히거나 채도를 올리지 않는다.
- 대비가 부족하면 먼저 프랍 뒤의 배경을 더 차갑고 어둡고 단순하게 조정한다.
- 별도의 밝은 림을 추가하지 않으며 원본 프랍에 존재하는 하이라이트만 유지한다.
- 발광 외곽선이나 네온 테두리는 사용하지 않는다.
- 2026-09-22 전력실 v2는 배전반 색을 바꾸어 구분 효과를 냈지만 사용자는 색 변경을 선호하지 않았다. 현재 시안은 그대로 유지하되 **황토/노랑 재도색을 신규 프랍의 표준으로 재사용하지 않는다.** 향후에는 배후 배경의 대비·광택·디테일을 먼저 정리하고, 프랍 자체 변경이 필요하면 별도 검토한다. 해당 결과의 상태는 `ART_ASSET_STATUS.md`가 관리한다.

### 캐릭터 팔레트

- 캐릭터는 장면에서 가장 강한 실루엣 대비를 갖는다.
- 붉은 후드와 호박색 바이저는 **플레이어**의 핵심 식별색으로 사용한다. 일반 인간 NPC는 얼굴과 직업별 복장을 드러낸다.
- 캐릭터의 식별색은 넓게 남발하지 않고 작은 집중 영역으로 유지한다.
- 인간 NPC의 비율·얼굴·복장 규칙은 `Docs/CHARACTER_ART_GUIDE.md`를 따른다.

## 4. 조명

다음은 원화 생성과 스프라이트 표현의 기본 지침이다. 승인 원화의 발광부·유리 반사·명암을 없애는 근거로 쓰지 않는다. 부드러운 전이를 픽셀 명암 단계로 옮길 때도 빛의 위치·범위·명도 관계를 보존하고, 변화가 크면 비교 승인을 받는다. 엔진 광원·이펙트의 별도 정책은 §10을 따른다.

- 조명은 소수의 명확한 광원으로 구성한다.
- 따뜻한 조명은 작업 대상과 캐릭터 주변에 제한적으로 사용한다.
- 빛과 그림자는 부드러운 그라데이션 대신 단계적인 픽셀 클러스터로 표현한다.
- 블룸, 렌즈 효과, 흐림, 피사계 심도는 사용하지 않는다.
- 조명 때문에 프랍과 배경의 고유 팔레트가 다시 동일해지지 않도록 한다.

## 5. 프랍 설계

원화 생성 단계의 설계 기준이다. 승인 이후에는 원화에 있는 구조를 보존하며, 아래 규칙으로 새 부품·측면을 추가하거나 기존 비율을 재설계하지 않는다. 충돌이 있다면 §0에 따라 먼저 보고한다.

- 한눈에 기능을 알 수 있는 단순한 외곽선을 우선한다.
- 마모와 손상은 소수의 큰 패치와 긁힘으로 표현한다.
- 작은 장식이나 표면 노이즈보다 문, 손잡이, 서랍, 팔걸이처럼 기능을 설명하는 부위를 강조한다.
- 동일 공간의 프랍은 색의 온도와 외곽선 굵기를 공유한다.
- 투영 기준은 `workshop_cabinet_reference_projection_v2.png`와 `workshop_armchair_reference_projection_v2.png`다.
- 캐비넷과 소파처럼 정면 실루엣을 우선하되, 윗면·측면·팔걸이·다리의 깊이 차가 몇 픽셀 드러나는 약한 원근을 유지한다.
- 책상처럼 정면만 보이는 평면적 프랍은 기준 프랍과 같은 방향으로 윗면과 측면 깊이를 소량 추가한다.
- 같은 방향의 평행 모서리는 일관된 소실 방향을 갖고, 물체들의 눈높이·바닥 접촉 관계가 맞아야 한다. 방향이 다르게 놓인 물체의 소실점까지 하나로 강제하지 않는다. 발 접지선·화면 중심을 지평선으로 간주하거나 원근을 없애서 접지 문제를 해결하지 않는다.

## 6. 환경 구성

- 방 하나는 하나의 연속된 플레이 공간으로 읽혀야 한다.
- 프랍 사이에 캐릭터가 이동할 수 있는 빈 바닥 공간을 남긴다.
- 천장 프레임, 벽, 바닥 구조는 방을 감싸되 프랍의 외곽선을 침범하지 않는다.
- 배경 디테일은 프랍이나 캐릭터보다 시선을 끌지 않아야 한다.
- 고정 설비·상호작용 프랍·근경 장식의 역할을 원화 브리프에 먼저 기록한다. 큰 코일이나 배전반처럼 기계로 보인다는 이유만으로 조작 가능하다고 가정하지 않는다. 시안용 가정과 실제 게임 기능은 구별한다.
- 큰 건축·설비 → 중간 연결 구조 → 국소 디테일 순서로 구성한다. 작은 소품을 늘리거나 벽 패턴을 조밀하게 반복하는 것으로 큰 조형을 대체하지 않는다.

## 6-1. 캐릭터 애니메이션

- 모든 애니메이션 프레임은 동일한 셀 크기와 Bottom Center 피벗을 사용한다.
- 프레임의 최하단 발 또는 신체 접촉 픽셀을 셀의 공통 바닥선에 맞춘다.
- 무기나 팔이 좌우로 뻗어도 몸통과 바닥 피벗 위치는 이동시키지 않는다.
- 러프 키프레임 단계에서는 클립당 3~4프레임을 기본으로 하며 과도한 보간 동작을 추가하지 않는다.
- 아이들은 호흡과 후드·머리카락·소매·팔의 작은 변화만 사용한다.
- 걷기는 접지, 통과, 반대쪽 접지 자세가 명확히 구분돼야 한다.
- 사격은 준비, 반동, 최대 반동 또는 총구 화염, 복귀 순서로 읽혀야 한다.
- 숙이기는 서 있는 자세에서 낮은 실루엣으로 전환되며, 방향과 바닥 피벗을 유지한다.

## 7. 모듈형 룸 블록

- 방 하나를 게임 공간을 조립하는 기본 블록으로 취급한다.
- 각 블록은 조립 가능한 천장, 좌우 연결 경계와 연속 바닥을 가진다. 제작상의 완결된 경계와 실제 카메라에 방 외곽 전체를 보여주는 구도는 별개이며, 신규 방에 외부 암부 여백을 강제하지 않는다.
- 좌우 벽 끝은 인접 블록과 연결하기 쉬운 명확한 수직 경계로 정리한다.
- 테마마다 건축 배경과 프랍을 함께 설계하고 고정 배경/상호작용의 역할을 구분한다. 서로 다른 색상군을 의무화하지 않고 승인된 고유색을 보존한다.
- 기존 차가운 배경과 난색 프랍의 관계는 유효한 그림체 참조지만, 새 방 또는 승인 원화를 그 팔레트로 강제 치환하지 않는다.
- 역할 분리는 배후 면의 단순화와 국소 대비, 기존 실루엣·기능 부위의 판독성으로 확보한다. 발광 외곽선, 프랍 전체 밝기 증가, 일괄 재색칠을 기본값으로 쓰지 않는다.
- 장면에 캐릭터가 없어도 이동 가능한 바닥과 프랍 사이 통로가 명확히 읽혀야 한다.
- 블록마다 실루엣과 팔레트는 달라도 카메라 거리, 픽셀 밀도, 외곽 프레임 비율은 공유한다.
- 모든 방과 복도 블록은 동일한 상대적 바닥 높이를 공유한다.
- 좌우 연결부에는 배경 디테일과 프랍을 두지 않는 단순한 수직 도어 소켓 영역을 확보한다.
- 빈 복도는 테마 방 사이의 시각적 휴지 공간으로 사용하며, 가구나 이동을 방해하는 프랍을 배치하지 않는다.
- 연결 문은 방 팔레트에 종속되지 않는 중립적인 어두운 금속색을 사용한다.
- 문은 독립된 투명 스프라이트로 관리하며 방 또는 복도 블록의 도어 소켓 위에 배치한다.
- 현재 기본 연결 문은 닫힌 양분할 슬라이딩 방폭문이다.

### 문 유형

- 정면문은 뒤쪽 벽에 설치하며 다른 깊이의 공간이나 목적지로 이동하는 출입구다.
- 측벽문은 좌우 벽 경계에 설치하며 같은 평면에서 연결된 방과 복도 사이를 차단한다.
- 정면문은 넓은 정면 실루엣, 측벽문은 얇은 수직 실루엣으로 즉시 구분되어야 한다.
- 두 문은 동일한 중립 금속 팔레트를 공유할 수 있지만 형태와 배치 피벗은 별도로 관리한다.
- 측벽문 앞면을 가독성을 이유로 사선 또는 3/4 시점으로 노출하지 않는다.
- 닫힌 측벽문은 벽 단면과 일직선인 얇은 차단선, 잠금 상태등, 천장 수납부와 바닥 레일로 표현한다.
- 열린 측벽문은 문짝을 벽 속에 숨기고 프레임·레일·열림 상태등만 남겨 통로를 표시한다.
- 정면문은 Back Wall 레이어, 측벽문은 Side Boundary 레이어에 배치한다.

### 배경 타일

- 실내 배경의 첫 구현 단위는 천장부터 기초까지 포함하는 세로 매크로 타일로 한다.
- 타일은 좌측 캡, 중앙 벽 변형, 반복 벽, 우측 캡으로 나눈다.
- 중앙 벽 타일에는 조명·환기구·큰 균열을 매번 포함하지 않는다.
- 눈에 띄는 배경 요소의 연속 복제를 피하기 위해 무장식 변형과 좌우 반전 변형을 섞는다.
- 모든 타일은 동일한 바닥선과 높이를 공유한다.
- 프랍은 투명 스프라이트로 배경 타일과 분리하고 Bottom Center 피벗을 기본으로 한다.

### 프랍 접지

- 프랍의 수치상 바닥 좌표뿐 아니라 눈에 보이는 최하단 픽셀이 바닥과 맞닿아야 한다.
- 가구 다리와 캐릭터 발은 바닥 표면을 소량 침범하도록 개별 오프셋을 조정한다.
- 바닥 프랍에는 짧고 단단한 사각 픽셀 클러스터 형태의 접촉 그림자를 별도 레이어로 둔다.
- 접촉 그림자에 블러, 부드러운 타원, 반투명 그라데이션을 사용하지 않는다.
- 벽 부착물과 문에는 바닥 가구용 접촉 그림자를 적용하지 않는다.

## 10. 네이티브 픽셀 규격 — 4px 블록 (**현행 엔진 호환 프로파일**)

이 절의 4px·줌·크기표는 현재 구현된 방식이다. 원화 보존을 위한 새 해상도 프로파일은 §0의 손실 비교 및 합의 전까지 미확정이다. 아래 수치는 승인 원화를 희생하는 절대 제약이 아니지만, 대체 프로파일 구현 없이 임의로 바꿔 반입할 수도 없다.

이 절과 변경 이력에서 말하는 **Power Relay 방 폐기**는 당시 Native8/저해상도 렌더 실험을 뜻한다. 2026-09-22의 `research-images/comparison/power-relay-concept-*.png` 신규 원화 방향을 폐기한다는 뜻이 아니다. 새 콘셉트 역시 엔진 규격 변경이나 옛 렌더 실험 복원을 승인하지 않는다.

2026-09-18 렌더 프리셋 비교(픽셀레이트 이전 / 534×300 ×3 / 800×450 ×2 / 베이크 자산·풀해상도 / 원본 자산·2px 격자)로 **"베이크 자산 · 풀해상도"** 를 확정했다. 그림은 4×4 월드 px 단색 블록으로 정리된 픽셀 아트, 렌더는 창 해상도 그대로(`AppFlow.VIEW_SIZE` = 2240×900) 의 SubViewport ×1 이고 확대는 카메라 줌이 맡는다. 저해상도 뷰포트(534×300 ×3), 계단형 광원, 8px 방식 B(267×150 ×6) 와 Power Relay 방은 폐기한다.

기존 방식 A는 `Tools/bake_pixel_grid.py`로 게임 스케일 그림을 4×4 평균색 블록으로 굽는다. 신규 보존형 작업은 방식 N의 **합의된 네이티브 격자(1 이미지 px = 1 아트 px)**에서 승인 원화를 옮긴다. Native4 호환성까지 확인된 파일만 ×4 Nearest로 반입한다. 네이티브 제작 자체가 무손실을 보증하지 않으며 §0의 비교 검수가 필요하다. 기존 베이크 자산은 유지하되 신규 변환에 평균 베이크를 추가하지 않는다.

### 단위

| 단위 | 정의 |
|---|---|
| 아트 픽셀(art px) | 그림의 진짜 픽셀 1개. 도트 하나 |
| 월드 px | 게임 좌표. **1 art px = 4 월드 px** (고정) |
| 화면 px | 2240×900 창. **1 art px = 2~6 화면 px** — 줌에 따라 변한다 |

**화면 배율은 하나가 아니다.** 카메라 줌은 `ART_CELL(4) × zoom` 이 항상 정수가 되도록 "화면 배율 정수"에서만 고르고(`main.gd`의 `ZOOM_PRESETS`), 상황에 따라 다음 범위를 오간다.

| 상황 | 화면 배율 | 보이는 art px | 조작 |
|---|---|---|---|
| 넓게 | **×2** | 1120×450 | F3 |
| **표준 (기본)** | **×3** | 747×300 | F3 기본값 |
| 가깝게 | ×4 | 560×225 | F3 |
| 단말기 접속 | ×5 | 448×180 | 기본 +2단계 |
| 대화 클로즈업 | **×6** | 373×150 | 기본 +1~+3단계 |

그래서 그림은 **두 기준을 동시에 통과해야 한다.**

- **판독 기준 = ×2.** 가장 축소된 상태에서 실루엣, 기능부, 명암 단계가 읽혀야 한다. ×2 에서 사라지는 정보는 게임 정보로 쓰지 않는다.
- **노이즈 기준 = ×6.** 가장 확대된 상태에서 1 px 점·디더링·끊긴 외곽선이 지저분하게 드러나지 않아야 한다. 얼굴이 나오는 인물은 대화 줌이 사실상 기본 검수 배율이다.

한쪽만 보고 그리면 반드시 한쪽이 깨진다. 방 좌표계·바닥선·타일 규격은 줌과 무관하게 월드 px 기준 그대로다(RESOURCE_USAGE_GUIDE).

### 납품 형식 (방식 N — 권장)

- **네이티브 해상도로 그린다**: 이미지 1 px = 1 art px. 확대해서 넘기지 않는다.
- Aseprite에서 합의된 네이티브 격자로 원화를 옮긴다. 원화 가져오기·참조·오버레이·추적, 리샘플링/색 양자화의 보조 사용은 허용한다. 자동 결과는 초안이며 원화와 대조해 경계·군집·색을 픽셀 단위로 정리하고 검수한다. 직접 좌표를 찍었다는 이유로 새 디자인이 원화 변환을 대신할 수는 없다.
- PNG, RGBA. 알파는 **0 또는 255 만**. 반투명·안티앨리어싱·부분 알파 금지 (반입 스크립트가 걸러낸다).
- 월드 크기는 4 의 배수 = 네이티브 크기는 정수. 아래 크기표를 따른다.
- 파일명과 하위 폴더는 게임 자산(`GodotPrototype/assets/`)과 같게 두고, 네이티브 원본은 `Assets/GameReady/Native4/<같은 상대경로>` 에 보관한다.
- 편집 가능한 `.aseprite` 파일은 레이어·프레임·태그가 보존된 제작 원본이고, 같은 위치의 PNG/JSON은 CLI로 다시 만들 수 있는 납품 산출물이다.
- 반입: `python Tools/upscale_native4.py` (×4 Nearest → `GodotPrototype/assets/`) → `python Tools/build_normal_maps.py` → `GodotPrototype/run.bat`(헤드리스 임포트). 베이크는 거치지 않는다.
- 격자 정렬은 신경 쓸 필요 없다. 네이티브로 그리면 격자가 곧 그림이다.
- 세부 명령, 자동 검사와 실패 시 되돌아가는 지점은 `Docs/ASEPRITE_PIPELINE.md`를 따른다.

### 기존 자산 유지·재현 기록 (방식 A — 신규 보존형 제작에 사용하지 않음)

다음은 이미 반입된 게임 스케일 그림의 유지·재현 설명이다. `Tools/bake_pixel_grid.py`가 4×4 블록(크롤러 10×10)을 평균색으로 굽고 알파를 다수결로 자른다. 기존 게임 자산을 이번 문서 개정으로 바꾸지 않는다. **신규 승인 원화의 픽셀화 또는 완료된 네이티브 PNG에 이 베이크를 적용하지 않는다.** 아래는 과거 입력 조건이다:

- 세부는 **4 월드 px(1 art px) 단위**로. 그보다 가는 선·점·글자는 평균색으로 녹아 사라진다. 확실히 남기려면 8 월드 px 이상.
- 타일은 128px 이음새 때문에 **격자 오프셋 0 고정**이다. 4px 격자에서 어긋나게 그리면 경계가 반 칸 밀린다. 프랍·캐릭터는 도구가 오프셋을 찾는다.
- 그라데이션·반투명·부드러운 브러시는 넣지 않는다. 명암은 2~3단계 색 블록으로 미리 나눈다.

크기가 표와 다르게 필요하면 **월드 4 배수(네이티브 정수)** 만 지키면 된다. 바닥 접지 픽셀은 셀의 공통 바닥선에 맞춘다(§5, §6).

### 그리는 법 (art px 하나가 화면에서 2~6px 인 것을 전제로)

- **외곽선은 1 art px 로 전체를 둘러도 된다.** ×2 에서도 1 화면 px 이 아니라 2 화면 px 이라 끊기지 않고, ×6 에서도 굵어 보이지 않는다. 캐릭터·상호작용 프랍은 실루엣 대비를 위해 두르고, 배경 타일은 어두운 쪽(접촉면·그늘)에만 두어 프랍과 위계를 나눈다.
- **세부는 1 art px 부터 허용, 장식 점은 2×2 권장.** 1 px 볼트·긁힘은 ×3 이상에서 또렷하지만 ×2 에서는 거의 사라지고 ×6 에서는 티끌처럼 튄다. **정보를 지닌 요소는 2×2 이상**, 1 px 은 질감 보조로만 쓴다. 균열은 폭 1·길이 4 이상.
- **팔레트는 자산 종류에 따라 결정한다.** 캐릭터는 배경과의 차별화를 위해 8~16색 목표를 유지한다. 배경·프랍은 원화 보존에 필요한 수를 정하며 공통 상한을 두지 않는다. 재질별 명암·반사·기능색을 구분하고 사용 색과 검사 상한을 기록한다. 목표와 승인 원화 보존이 충돌하면 임의 감색 대신 재검토한다(§0, §3).
- **음영은 계단.** 디더링(체커)은 넓은 면의 2단계 경계에 한 줄까지만. 대화 줌(×6)에서는 체커가 그대로 무늬로 보이므로, 인물과 클로즈업에 잡히는 프랍에는 디더링 대신 색 단계를 하나 더 넣는다. §9 의 "매끈한 그라데이션 금지" 는 유지.
- **글자는 그리지 않는다.** 32 px 타일에 읽히는 글자를 넣을 수 없다. 표지판은 색 블록과 아이콘 실루엣으로.
- **플레이어와 얼굴을 가린 인물**은 바이저 3×1~4×2 art px 정도로 식별한다. **일반 인간 NPC**는 얼굴을 드러내되 눈 1개·코·턱을 소수의 큰 픽셀 클러스터로 표현한다. 얼굴은 대화 줌(×6)에서 가장 크게 보이므로 그 배율에서 표정이 깨지지 않는지 함께 본다. 세부 기준은 `Docs/CHARACTER_ART_GUIDE.md`.
- **애니메이션은 프레임으로.** 1 art px 이동이 ×6 에서는 6 화면 px 이라 작게 잡은 움직임도 또렷이 보인다. 대기 호흡·걷기 모두 코드 스케일 대신 프레임으로 그린다(아래 "런타임 변형"). 걷기 4프레임은 다리 위치가 1 px 이상 바뀌게.
- 벽 타일은 **이음새 격자에 무늬를 맞춘다.** 32 px 안에 벽돌 2×1 이 정확히 4줄처럼 타일 경계에서 무늬가 나누어지게. 4방 타일링 검사는 네이티브 크기에서 한다.

### 런타임 변형 — 스케일·회전 (**금지 규칙**)

그림을 아무리 네이티브로 그려도 엔진이 스프라이트를 비정수 배율로 줄이거나 임의 각도로 돌리면 그 자리에서 격자가 깨진다. Nearest 확대라 부드러워지지도 않고, 픽셀이 들쭉날쭉 뭉개진 채로 보인다. 그래서 자산 규격과 같은 무게로 코드 쪽에 다음을 고정한다.

- **스프라이트 `scale` 은 ±1 만.** 좌우 반전(`scale.x = -1`)과 등배만 허용한다. 0.4·1.05 같은 값은 art px 이 1.6 월드 px, 4.2 월드 px 이 되어 화면에서 블록 크기가 어긋난다.
- **`rotation` 은 0 과 90° 배수만.** 그 외 각도는 **베이크 프레임**으로 만든다. 센트리 헤드의 각도 팬처럼 필요한 각마다 그림을 따로 뽑고, 코드는 프레임을 고르기만 한다.
- **스쿼시·스트레치, 호흡, 끄덕임, 반동은 프레임으로 그린다.** 코드에서 몸통을 눌러 만든 호흡은 픽셀 아트가 아니라 고무 인형처럼 보인다. 프레임이 없어 임시로 코드 변형을 쓰는 동안에는 그 사실을 자산 README 에 적고 프레임 제작 대기 목록에 올린다.
- **불가피한 예외는 문서에 남긴다.** 예외를 코드에만 두지 않는다. 현재 기록된 예외는 아래 둘이고, 둘 다 해소 대상이다.

| 예외 | 현재 상태 | 해소 방향 |
|---|---|---|
| 크롤러 `SCALE = 0.4` (`crawler.gd`) | art px 이 1.6 월드 px — 유일하게 격자가 다른 자산 | 크기표대로 셀 64×48 로 다시 그리고 스케일 1.0. `MOUTH_LOCAL`·히트박스 재측정 |
| 센트리 헤드 연속 회전 (`sentry_turret.gd`) | 베이크 각 3단계 + 그 사이는 임의 라디안 회전 | 각도 팬을 촘촘히 뽑아 프레임 선택만 남기고 `rotation` 제거 |

플레이어 호흡(`player.gd`)처럼 프레임 애니메이션이 준비된 자산은 코드 변형을 끈다. NPC 는 프레임이 있으면 `scale` 을 1 로 두는 처리가 이미 들어가 있다(`npc.gd`) — 같은 기준을 플레이어에도 적용한다.

### 조명·이펙트 (코드 쪽)

- 광원 고리(`Lighting.radial_texture`)·글로우·파티클·카메라 이동은 풀해상도에서 부드럽게 둔다. 픽셀 격자에 스냅하지 않는다 — 그림만 픽셀이고 빛과 움직임은 매끄러운 것이 이 스타일의 핵심.
- 코드가 월드 px 로 그리는 것(조준점, 파편, 탄피, 불 셰이더 `pixel_step`)은 4 배수로 두어 art px 격자와 맞춘다.

### 이행 순서

1. **코드 확정**: 렌더 프리셋을 "베이크 자산 · 풀해상도" 하나로 고정하고 저해상도 뷰포트·계단형 광원·뷰 px 상수·Power Relay 방·Native8 자산을 제거한다. `assets_original/` 비교 폴더도 삭제한다(원본은 커밋 314190d 에서 언제든 꺼낼 수 있다).
2. **기존 자산은 그대로**(베이크본 유지). 다시 그릴 필요 없다.
3. **새 자산부터 방식 N**: `Assets/GameReady/Native4/` 에 네이티브로 그려 `Tools/upscale_native4.py` 로 반입. 기존 자산을 교체할 때도 같은 파일명으로 넣으면 좌표·타일셋은 건드리지 않는다.
4. 우선순위: 베이크에서 가장 뭉개졌던 순서 — ① 문 손잡이·캐비넷 디테일 등 프랍 ② 벽 표지판(글자 → 색 블록) ③ 캐릭터 분리 프레임 ④ 크롤러(새 셀 64×48, 스케일 1.0) ⑤ 타일. 넓은 색면 프랍(소파·작업대)은 베이크본으로 충분해 마지막.

### 제작·검수 순환

모든 단계는 §0의 **원화 생성 → 사용자 승인 → 보존형 픽셀화** 뒤를 따른다. 아래 구조/재질 패스는 원화를 충실하게 옮기는 작업 순서이지 새로운 디자인을 발명하는 순서가 아니다.

1. **최신 규격·비교군 고정:** 이 문서와 실제 런타임 경로를 읽는다. 같은 역할의 기존 프랍을 고르고 경로·해시·아트 격자·실루엣 크기를 기록한다. 프랍 작업은 [`PROP_STYLE_REVIEW.md`](PROP_STYLE_REVIEW.md)의 분석 및 시험 기록을 먼저 읽는다.
2. **브리프 고정:** 승인 원화 파일·해시·대상 영역과 보존 목록을 고정한다. 손실 비교 뒤 캔버스, 피벗·접지, 팔레트와 출력 프로파일을 정한다. 원화 충실도·규격·게임 적합성은 별도 합격 조건이다.
3. **단계별 네이티브 제작:** 실루엣 → 두께·구조 → 재질·기능 → 국소 마감 순서로 Aseprite에서 작업한다. Lua도 동일한 단계와 시각 검수를 거친다. 시험본은 `Assets/Generated/`의 버전별 폴더에 저장하고 기존 원본을 덮어쓰지 않는다.
4. **내보내기·규격 검사:** PNG/JSON을 CLI로 내보내고 크기·색·알파·경계·프레임을 검사한다. `.aseprite`를 다시 열어 내보낸 PNG와 픽셀 단위로 일치하는지도 확인한다. 성공 상태는 **규격 통과**일 뿐이다.
5. **반입 전 보존·스타일 게이트:** 승인 원화 / 픽셀화 후보를 비교해 색·형태·부품·재질·세부 손실을 먼저 기록한다. 이어 같은 art px 배율의 기존 프랍 / 후보를 비교한다. 현행 프로파일의 1×·화면 ×2·×3·×6·흑백을 확인하고, 새 프로파일은 합의한 배율로 별도 표시한다. 보존 실패면 규격을 재검토하고, 원화 자체의 변경이 필요하면 재승인을 받는다. 반입은 중단한다.
6. **조립·플레이어 게이트:** 실제 배경과 플레이어로 비교한다. 오프라인 조립은 색·규모의 예비 검토이지 엔진 조명·피격·가림 검증이 아니다. 배경 대비 문제를 프랍 전체 밝기 증가로 해결하지 않는다.
7. **명시적 반입·엔진 검수:** 승인 및 현행 월드 크기 호환성을 확인한 파일만 Native4에 승격한 후 ×4 Nearest 월드 출력, 노멀맵, 엔진 임포트를 갱신한다. 다른 프로파일 후보는 별도 합의·구현 검증 전까지 staging에 둔다. ×4는 파일의 월드 배율이며 화면 줌 기준을 대체하지 않는다. 게임의 ×2·×3·×6, 접지·가림·조명·스케일/회전을 확인한 뒤에만 **런타임 승인**으로 기록한다. 관련 없는 타일·다른 프랍을 함께 재생성하지 않는다.

## 11. 원화에서 게임 리소스로 전환할 때의 밀도 검수

승인된 원화는 색·형태·디자인·디테일의 직접 기준이다. 픽셀화와 게임 적용은 별도 검수하지만, 그 검수를 명목으로 원화를 임의 재해석하지 않는다. 타일의 모듈화처럼 원화와 다른 구성이 필요하면 변경 범위를 사전 합의한다.

### 가장 먼저: 원화 보존 비교

- 원본 전체와 대상 크롭을 보존하고 파일·해시·크롭 좌표를 기록한다. 원화의 화면/병/손잡이/바퀴 등 핵심 부품 목록과 각 재질의 명암·색 관계를 비교한다.
- `원화 / 픽셀화 후보`의 같은 표시 크기 비교와 주요 부위 확대·오버레이를 만든다. 크기 정규화는 **충실도 비교용**임을 표시하고 실제 게임 배율 비교와 혼동하지 않는다. 후보 확대는 Nearest 정수 배율을 유지하고 원화 표시 변환도 기록한다.
- 평가 항목은 실루엣·비율·부품 배치, 색감·명도 위계, 입체감·재질, 디테일의 정체성과 밀도다. 서로 다른 물체처럼 보이거나 부품이 사라지면 규격 검사 성공과 무관하게 실패다.
- 불가피한 손실/변경, 해상도·팔레트 대안, 사용자의 선택을 기록한다. 반복 수정 중에도 승인 원화를 직접 비교하며 직전 실패본만을 기준으로 삼지 않는다.

### 기준 리소스와 비교

- 신규 환경 세트는 원화만 보지 않고 **같은 아트 픽셀 배율**의 기존 런타임 리소스와 나란히 비교한다. 서로 다른 크기의 물체를 같은 바운딩 박스로 늘려 맞추지 않는다. 면밀한 형태 비교를 위해 별도 크기 정규화를 했다면 보조 이미지로 표시하고 배율 검수에는 사용하지 않는다.
- 환경 프랍의 밀도 기준은 `workshop_workbench_game_scale.png`, `workshop_locker_game_scale.png`와 현재 게임용 작업실 프랍이다.
- 배경 타일의 밀도와 명암 기준은 `workshop_modular_background_sheet_3x2.png` 및 실제 조립 프리뷰다.
- 비교할 때 팔레트와 청결도는 달라도 된다. 실루엣 복잡도, 명암 단계, 재질 단차, 접촉 그림자와 픽셀 군집 크기는 같은 계열로 읽혀야 한다.
- 프리베이크 `Assets/GameReady/Props/`와 실제 `GodotPrototype/assets/props/`를 혼용하지 않는다. 기존 베이크본의 격자 위상을 찾아 **손실 없이** 비교용 art px를 추출한다. 불일치가 있으면 중지하고 원인을 기록한다. 기준 파일 목록과 측정 방법은 `PROP_STYLE_REVIEW.md`를 따른다.
- 색상 수, 불투명 면적, 인접 픽셀 변화율은 진단 보조값이다. 수치가 높다고 고품질이 아니며, 노이즈로 올린 밀도는 실패다. 기존 베이크본의 수천 가지 미세 RGB를 신규 팔레트 목표로 삼지 않는다.

### 깨끗한 시설의 표현 규칙

- **깨끗함은 단색 사각형을 뜻하지 않는다.** 오염 대신 패널 단차, 고무 실, 볼트, 환기구, 손잡이, 유리 두께, 접합 그림자와 모서리 하이라이트로 밀도를 만든다.
- 프랍은 대형 실루엣, 중형 구조물, 소형 기능 디테일의 세 단계가 모두 있어야 한다. 한 단계라도 없으면 블록아웃으로 판정한다.
- 프랍의 주요 재질은 최소 3단계 명암으로 나눈다. 외곽선·접촉 암부와 발광색은 이 명암 단계와 별도로 둔다.
- 넓은 평면은 그대로 비워 둘 수 있지만, 외곽 단차나 한쪽 면의 그림자가 있어 두께가 읽혀야 한다. 장식 점을 흩뿌려 빈 면을 메우지 않는다.
- 발광색은 기능부에만 제한한다. 프랍 전체 윤곽을 발광색으로 두르지 않는다.

### 타일 밀도와 반복 규칙

- 32×32 배경 타일의 네 모서리와 가장자리는 동일한 기본색으로 이어지게 한다. 모든 타일에 테두리를 그려 32px 체크무늬가 드러나게 하지 않는다.
- 3×2 배경 시트는 무작위 변형 6장이 아니라 **96×64 매크로 패널 한 장을 여섯 셀로 자른 것**으로 취급한다. 조립 시 `(x mod 3, y mod 2)` 위상을 유지한다.
- 환기구, 표시등, 버튼, 경고 아이콘처럼 의미가 있는 디테일을 각 32px 셀에 넣지 않는다. 이런 요소는 별도 프랍이나 희소 장식 레이어로 배치한다.
- 패널 이음새와 베벨은 여러 셀을 가로지를 수 있다. 32px 저장 격자가 아니라 64~128px 규모의 건축 패널이 먼저 읽혀야 한다.
- 디테일은 타일 안에 존재하되, 조립한 방에서는 큰 벽면이 먼저 읽혀야 한다. 반복 무늬가 프랍의 외곽선보다 강하면 실패다.
- 프레임 타일은 배경보다 어둡고 두꺼워야 하며, 최소 `deep → line → shade → light`의 네 역할이 구분되어야 한다. 직선 프레임의 슬롯·램프·볼트를 매 셀마다 반복하지 않는다.
- 타일 한 장의 정보량만 확인하지 않는다. 반드시 12×6 이상으로 반복 조립해 격자 노출, 지나친 반복, 프랍과의 대비를 검사한다.

### 승인 게이트

0. **원화 보존:** 승인 원화와의 직접 비교, 핵심 부품·컬러·형태·디테일 유지, 불가피한 변경의 사용자 승인. 통과 전에는 작은 캔버스로 일괄 제작하지 않는다.
1. **규격:** 합의된 네이티브 크기·팔레트·알파·피벗·원본 재출력. 자동 검사에만 근거해 “아트 완료”라고 말하지 않는다.
2. **스타일:** 기존 / 수정 전 / 후보 비교 증거와 1×·×2·×3·×6·흑백 검토. 대형·중형·소형 정보, 약한 원근, 재질 단계, 휴지 면적을 항목별로 평가한다. 색 수가 아니라 픽셀의 역할을 확인한다.
3. **조립:** 배경·프레임·프랍·플레이어의 위계와 접지. 중립 배경 단독 샷이나 오프라인 접지 시트만으로 완성된 방을 승인하지 않는다.
4. **런타임:** 실제 엔진의 줌·조명·가림·상호작용. 실행하지 못했다면 미검증으로 적는다.
5. **증거 기록:** 콘셉트 승인 / 규격 통과 / 스타일 검토 / 런타임 승인을 구분한다. 기준·후보 파일의 해시, 실제 본 이미지, 남은 결함을 기록하며 단순 파일 생성이나 검사 출력은 시각 검수의 증거가 아니다.

연구시설 프랍 원화 `Assets/Generated/ResearchFacilityV2/`의 3개 props 시트는 §0의 **형태·색·재질·디테일 보존 기준**이다. 기존 `Native4/Props/research_*/*.aseprite`와 검토용 PNG는 이전 저밀도 산출물이며 승인 기준이 아니다. `Assets/Generated/PropStyleLab/`의 비교·구조 시험도 원화 보존형 전환의 성공 사례로 취급하지 않는다. 실패 기록은 `PROP_STYLE_REVIEW.md`에 보존한다.

### 형태 잠금 게이트 — 기계 프랍

규격을 맞추고 디테일을 늘려도 원화와 다른 그림일 수 있다. 재질 패스 **전에 승인 원화에서** 중심축, 부품 연결, 두께, 접지와 반복 부품의 위치를 추적하고 원화와 대조한다. 구조 사본 검토는 보존 확인용이다. 원화를 정형 상자·고정 깊이 벡터·동일 마스크로 강제 재설계하지 않는다. 원화에 구조적 모순이 있으면 픽셀화 중 임의로 고치지 말고 수정 승인을 요청한다.

- 같은 방향의 면과 곡면·비대칭은 원화의 투영을 따른다. 원화에 없는 모서리 절삭이나 상판 기울기 변경을 추가하지 않는다.
- 직선은 곧게, 사선은 일관된 계단 길이로, 곡선은 점진적으로 변하는 계단으로 정리한다. 외곽의 이중 두께와 이유 없는 1px 돌출을 확대 검토한다.
- 명암은 면 방향과 광원을 설명해야 한다. 윤곽 전체를 따라 밝은 띠를 두르는 banding, 중심만 밝히는 pillow shading, 평면을 찌그러져 보이게 하는 임의의 명암 조각을 피한다.
- 기능·재질·마감 레이어는 확정된 구조의 범위 안에서 작업한다. 실루엣 변경이 필요하면 구조 단계로 돌아가고 다시 비교한다. 단순 덧칠로 가리지 않는다.
- 이진 알파와 AA 금지는 현행 납품 규칙이며 모든 픽셀아트의 보편 규격은 아니다. 배경·프랍의 8~16색 일괄 상한은 적용하지 않으며 캐릭터의 8~16색 목표는 유지한다. 색 수·PNG 치수 검사는 원화 보존이나 형태 품질을 증명하지 않는다.

일반 기법 참고: 아티스트 cure의 [The Pixel Art Tutorial](https://pixeljoint.com/forum/printer_friendly_posts.asp?TID=11299) — 군집·jaggies·banding·노이즈. [Aseprite Context Bar](https://www.aseprite.org/docs/context-bar/)의 Pixel-perfect stroke는 그리기 도구 옵션이며 부품 구조와 원근을 자동으로 교정하는 기능은 아니다. 실제 교정 좌표와 비교는 [추가 프랍 기록](../Assets/Generated/PropStyleLab/batch2/README.md)에 있다.
